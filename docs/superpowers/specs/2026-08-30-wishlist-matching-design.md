# Вішліст бажань із матчингом

**Дата:** 2026-08-30
**Статус:** спроєктовано, чекає на план
**Обсяг:** модуль №2 суперапу — приватні відповіді, збіги, звʼязок із рандомайзером поз

---

## 1. Контекст

`WRNRS / між нами.` — живий Telegram-бот для пар. На момент цього спека вже є:

- **каркас модулів** (`internal/catalog`, `internal/modules`) — фасетні каталоги, детермінований вибір без повторів, гейт доступу, реєстр із диспетчеризацією за префіксом колбека;
- **модуль поз** — 519 позицій двома мовами, картинки в MinIO, фасетні фільтри, спільні для пари відмітки (`pair_position_marks`), крутилка, масова відправка;
- гра в картки, паринг, теми, Telegram Stars, адмінка.

Бот працює соло: онбординг завершується без пари, а модуль поз має `NeedsPair: false`.

Цей модуль — етап 2 карти суперапу зі спека `2026-08-29-couples-superapp-positions-design.md`.

---

## 2. Мета й головна ставка

Обидва партнери приватно відмічають, чого хочуть. Бот показує **лише збіги**. Партнер ніколи не дізнається, що ти сказав «Ні».

Ставка в тому, що це прибирає найдорожчий барʼєр у розмові про близькість — потребу озвучити бажання першим і ризикнути відмовою. Побічний ефект не менш важливий: збіги по позах перетворюють рандомайзер із «крутилки випадкового» на «крутилку того, що ви обидва хочете».

## 3. Зафіксовані рішення

| # | Рішення |
|---|---|
| Р1 | Два джерела: окремий каталог бажань (рівно 60 пунктів) і наявні 519 поз. |
| Р2 | Шкала: **Хочу / Цікаво / Ні**. |
| Р3 | Збіг = ніхто не сказав «Ні», і хоча б одне сказало «Хочу». |
| Р4 | Прогрес партнера не показується. Видно лише факт, що він почав. |
| Р5 | Власні текстові бажання **не входять** у v1. |
| Р6 | Відповіді належать **людині**, не парі: переживають розрив і працюють із новим партнером. |
| Р7 | Гейт `Needs18Plus + NeedsMature`, `NeedsPair: false`, `NeedsPremium: false`. |
| Р8 | Бажання гортаються окремим екраном; пози голосуються **ліниво** — кнопкою в наявному браузері поз. |

## 4. Архітектура

### 4.1 Нові файли

| Файл | Відповідальність |
|---|---|
| `content/wishes.v1.json` | каталог бажань у форматі `internal/catalog` |
| `internal/storage/wishes.go` | таблиця `wish_answers`, запис відповіді, читання своїх, обчислення збігів |
| `internal/wishlist/service.go` | чиста логіка: правило збігу, черга наступного невідміченого, статистика |
| `internal/wishlist/handler.go` | екрани модуля й роутинг колбеків |
| `internal/wishlist/keyboards.go` | клавіатури модуля |

### 4.2 Змінювані файли

| Файл | Зміна |
|---|---|
| `internal/positions/handler.go` | кнопка «хочу спробувати» на картці; фільтр «тільки збіги» |
| `internal/positions/keyboards.go` | згадані кнопка й пункт фільтра |
| `cmd/wrnrs/main.go` | завантаження каталогу бажань, реєстрація модуля |
| `internal/config/config.go` | `WISHES_CATALOG_PATH` |
| `content/i18n/{uk,en}.json` | рядки модуля |

### 4.3 Чому немає звʼязності модуль-у-модуль

Модуль поз читає збіги **через `internal/storage`**, а не через імпорт `internal/wishlist`. Обидва модулі вже залежать від сховища, тож нової звʼязності не зʼявляється, і жоден із них не знає про існування іншого.

## 5. Дані

```sql
CREATE TABLE IF NOT EXISTS wish_answers (
    user_id     INTEGER NOT NULL REFERENCES users(telegram_id) ON DELETE CASCADE,
    item_kind   TEXT    NOT NULL CHECK (item_kind IN ('wish', 'position')),
    item_id     TEXT    NOT NULL,
    answer      TEXT    NOT NULL CHECK (answer IN ('want', 'curious', 'no')),
    answered_at TIMESTAMP NOT NULL,
    PRIMARY KEY (user_id, item_kind, item_id)
);
```

- Ключ на користувачі — це і є Р6.
- `ON DELETE CASCADE` від `users`: видалення акаунта прибирає відповіді.
- Розрив пари відповідей **не чіпає** — на відміну від `pair_position_marks`, які тепер видаляються. Різниця свідома: відмітка «ми це пробували» належить стосункам, бажання належить людині.
- `item_kind` розділяє простори ідентифікаторів: `wish` `w001…`, `position` `001…519`.

### Правило збігу

```
match(a, b) := a != 'no' AND b != 'no' AND (a = 'want' OR b = 'want')
```

Сила збігу:
- 🔥 `want + want`
- ✨ `want + curious`

`curious + curious` збігом **не є**: якщо обом лише цікаво, це не сигнал до дії, і показ таких пар розмив би список.

## 6. Приватність

**Інваріант:** жодна окрема відповідь партнера не залишає сховища. Назовні віддаються тільки збіги й булеве «партнер почав».

Що з цього випливає для реалізації:
- немає жодного методу, що повертає відповіді іншого користувача;
- обчислення збігів робиться одним SQL-join'ом усередині сховища, назовні йде лише результат;
- лічильник партнера не показується ніде — це Р4.

**Залишкова дірка, яку не можна закрити.** Якщо обидва пройдуть **весь** каталог, партнер вирахує твої «Ні» відніманням: він знає свої відповіді й бачить збіги. Це властиве будь-якій системі «показуємо лише збіги», а не вада реалізації.

Помʼякшення: каталог великий, проходження цілком малоймовірне, а невидимість прогресу лишає «немає збігу» двозначним — чи сказав «ні», чи ще не дійшов. Обмеження документується в UI одним рядком, щоб очікування були чесними.

## 7. Екрани

Префікс колбеків: `wish:`

### Хаб `wish:open`
- `💛 Відмічати` — черга наступного невідміченого бажання
- `🔥 Збіги (N)` — список; без пари показує пояснення
- `📊 Мої відповіді` — свої відмітки з можливістю змінити
- статус: скільки відмічено з N; окремим рядком «партнер теж відмічає», коли це так

### Гортанка `wish:next` / `wish:answer:{kind}:{id}:{answer}`
Одне бажання за раз: назва, короткий опис, група. Кнопки `💛 Хочу` · `🤔 Цікаво` · `🚫 Ні`, плюс `⏭ Пропустити` (не зберігає відповідь) і `⌂ Меню`.

Порядок черги — детермінований: спершу за інтенсивністю (`gentle` → `medium` → `bold`), за рівної інтенсивності — за зростанням `ID`. Так людина може зупинитись будь-коли, а не наткнутись на різке з першого екрана, і черга не «стрибає» між заходами.

### Збіги `wish:matches`
Список збігів обома типами разом, із позначкою сили. Для позицій — перехід у картку в модулі поз.

### Свої відповіді `wish:mine`
Список власних відміток, згрупований за відповіддю. Зміна відповіді — тим самим колбеком, що й у гортанці.

### У модулі поз
- на картці позиції зʼявляється кнопка бажання, що пише `wish_answers` із `item_kind='position'`;
- у фільтрах зʼявляється перемикач «тільки збіги», який звужує вибірку до збігів пари.

**Увага реалізатору.** «Тільки збіги» — це **не фасет**. `catalog.Filter` оперує значеннями фасетів із самого каталогу, а збіги живуть у базі й залежать від пари. Тому перемикач не можна впхнути в `Filter.Include`: він застосовується окремим кроком **після** `Filtered()`, у тому ж місці, де `VisibleWithMarks` уже відсіює приховані позиції. Стан перемикача зберігається в `BrowseState` поряд із фільтром, а не всередині нього. Без пари перемикач неактивний.

## 8. Контент

`content/wishes.v1.json` у форматі `internal/catalog`: рівно 60 елементів, обидві мови обовʼязкові (`Validate([]string{"uk","en"})`).

Фасети:
- `kind` — `place` (місце), `role` (роль), `pace` (темп), `mood` (атмосфера), `toys` (іграшки), `scenario` (сценарій)
- `intensity` — `gentle`, `medium`, `bold`

ID — `w001`…`w060`, **нуль-доповнені**: `catalog.Filtered` сортує лексикографічно, і неподовжені числа дали б порядок `w1, w10, w100`.

Тон — як у каталозі поз: фактично, тепло, без вульгаризмів і без медичного канцеляриту. Кожне бажання формулюється так, щоб на нього можна було відповісти «Хочу / Цікаво / Ні» без додаткових пояснень.

---

## 9. Що НЕ входить

- власні текстові бажання (Р5) — і разом із ними питання про `Handler.HandleMessage` без стану FSM, яке лишається відкритим до модуля, що справді читатиме текст;
- голосування по всіх 519 позах суцільною гортанкою (Р8);
- сповіщення партнерові про новий збіг — розглянути після того, як стане видно, чи модулем узагалі користуються;
- монетизація.

---

## 10. План тестування

- Правило збігу: усі девʼять комбінацій двох відповідей; окремо перевірити, що `curious + curious` збігом не є.
- Приватність: у сховищі немає методу, що віддає чужу відповідь; тест на те, що результат обчислення збігів не містить індивідуальних відповідей.
- Відповіді переживають розрив пари й працюють із новим партнером.
- Видалення акаунта каскадно прибирає відповіді.
- Соло: гортанка й запис працюють без пари; екран збігів без пари показує пояснення, а не порожній список.
- Черга: наступне невідмічене йде за зростанням інтенсивності; пропуск не зберігає відповідь і не блокує повторний показ.
- Каталог: 60 елементів, ID нуль-доповнені й відсортовані, обидві мови присутні.
- Модуль поз: кнопка бажання пише `item_kind='position'`; фільтр «тільки збіги» звужує вибірку і не ламає наявні фасетні фільтри.
- i18n: набори ключів обох мов симетричні.

## 11. Ризики

**Порожній модуль.** Якщо ніхто не відмічає, збігів немає й фіча мертва. Помʼякшення: соло-відмічання (Р6) дозволяє заповнити вішліст до появи пари, а ліниве голосування по позах (Р8) не потребує окремого заходу — людина й так гортає каталог.

**Каталог як редакційне рішення.** 60 бажань задають, що взагалі можна захотіти. Занадто мʼякий список зробить модуль беззмістовним, занадто різкий — відлякає. Мітигація: поле інтенсивності й порядок від мʼякшого, щоб різке треба було свідомо догортати.

**Асиметрія відповідей.** Якщо одне відмітило 60, а друге 3, збігів майже не буде, і активніший вирішить, що партнерові нецікаво. Мітигація: показувати факт «партнер теж відмічає» (Р4) і формулювати порожній екран збігів як «ще рано», а не як «нічого не збіглося».
